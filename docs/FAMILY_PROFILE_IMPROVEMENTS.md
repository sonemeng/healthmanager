# 家庭健康档案改进计划与实现规范

## 目标与术语

将一个登录账号下的健康数据明确划分为独立档案，避免查看、录入、导出和 AI 分析时混入其他成员的数据。

- 本人档案：与登录账号一一对应，不可删除；当前为“吴菊兰”。
- 家庭成员：由本人添加和管理的独立档案；当前包括“刘丙友”“刘文龙”。
- 当前档案：用户正在浏览、录入和分析数据的档案，由 `hm_profile` cookie 指定。
- 账号级设置：登录、AI 渠道、通知和应用偏好，不随当前档案切换。
- 档案级数据：检验指标、导入报告、用药、病史、就诊、时间线、复查、AI 上下文、导出与分享。

## 现状与约束

- `profiles` 已承载本人和家庭成员，`is_default=true` 表示本人档案。
- 健康业务表已有 `profile_id` 的包括 `observations`、`import_jobs`、`medications`、`conditions` 和 `encounters`。
- 当前档案由服务端验证 cookie 归属，所有新增查询必须使用该服务端解析结果，不能信任浏览器传入的档案 ID。
- 历史数据已校正：吴菊兰为本人档案，拥有 87 条指标与 9 份报告；刘丙友和刘文龙为独立家庭成员。

## 改进项

### 1. 全站当前档案身份条

**范围**：所有 Dashboard 健康页面。

**实现**：在 Dashboard 主内容顶部渲染 `ProfileContextBar`。它读取 `profiles.active`，显示头像、`正在查看`、姓名和“本人/家庭成员”身份；家庭成员状态提供“返回本人档案”入口。

**验收**：切换至任意成员后，首页、检验、报告、AI、用药、病史、就诊、时间线均可在不阅读数据内容的情况下确认当前对象。

### 2. 家庭成员空档案引导

**范围**：首页，以及后续各健康模块的空状态。

**实现**：当前档案无指标时，首页显示“某某的健康档案尚无记录”，并提供导入报告、添加用药、记录病史、添加就诊入口。本人档案沿用常规新用户引导文案。

**验收**：刘丙友或刘文龙无数据时，不展示吴菊兰的任何统计卡片或预览，并能直接开始建档。

### 3. 导入前档案归属确认

**范围**：报告上传页、模块导入按钮、Apple Health 导入。

**实现**：上传页默认使用 `hm_profile`，不再读取过期的 localStorage 状态。选择目标仅影响本次导入；点击上传后展示确认卡，明确“本次 N 个文件将导入至：姓名”。服务端校验目标档案属于当前登录账号。

**验收**：用户必须在看见目标姓名后确认；无法通过篡改客户端 ID 向其他账号档案导入。

### 4. AI 当前服务对象与独立会话

**范围**：AI 问答、综合健康报告。

**实现**：AI 页显示“正在为某某分析健康数据”。切换档案后清空客户端会话状态；服务端以 `metadataJson.profileId` 隔离会话和综合报告，旧版无档案标签的结果不跨档案展示。

**验收**：不同成员之间无法在侧栏看到对方会话或综合报告；AI 输入上下文只来自当前档案。

### 5. 家庭健康概览

**范围**：新增 `/family` 页面及导航入口。

**实现**：每个档案仅展示低敏感概览：最近报告日期、待复查数、在用药数量、最近就诊日期、资料完整度。默认不展示具体化验数值。点击卡片切换到该档案首页。

**数据**：新增批量档案摘要服务端查询，按 `profile_id` 聚合，避免 N+1 查询。

**验收**：家庭概览不泄露具体检验值；每张卡片与档案详情的统计一致。

### 6. 成员级基础健康资料

**范围**：成员设置、AI 上下文、报告打印头。

**实现**：将性别、出生日期、身高、体重保留在 `profiles`；新增档案级血型、过敏史、紧急联系人、常用医院/医生、家族史字段或独立 `profile_health_details` 表。用户偏好中的个人生理资料逐步迁移到本人档案。

**验收**：生成家庭成员报告时不再显示登录账号的出生日期、血型或性别；AI 只使用该成员的人口学信息。

### 7. 安全的数据删除与转移

**范围**：成员管理。

**实现**：本人档案不可删除。删除家庭成员前必须选择“仅删除档案并保留未归属数据”或“永久删除档案及健康数据”，后者要求二次确认并显示数据数量。另提供“转移至本人/其他成员”操作。

**数据**：删除前由服务端统计并在单一事务中执行删除或转移；禁止静默 `ON DELETE SET NULL` 造成难以找回的数据。

**验收**：没有确认不会删除健康数据；所有转移结果可在目标档案摘要中核对。

### 8. 成员级导出与分享

**范围**：健康报告、分享中心。

**实现**：将“家庭健康摘要”更名为“当前档案健康摘要”，下载名包含档案姓名和日期。分享令牌永久绑定 `profile_id`，支持有效期、密码和随时撤销。

**验收**：从刘文龙档案导出的文件不会出现吴菊兰的数据或姓名；分享链接不能因切换当前档案而改变内容。

### 9. 首页数据状态分层

**范围**：首页。

**实现**：按当前档案数据量分为三种状态：无数据（建档引导）、少量数据（提示继续导入以启用趋势和分析）、完整数据（评分、异常、趋势、复查）。统计全部由当前档案服务端查询提供。

**验收**：新家庭成员看到可操作的引导；已有一份报告的成员不会被误判为完全无数据。

### 10. 统一术语与可访问性

**范围**：导航、设置、上传、报告、空状态、帮助文案。

**实现**：统一“本人档案”“家庭成员”“当前档案”文案；移除“主用户”“默认成员”等模糊称谓。档案切换器提供 `aria-label`、当前状态和键盘可用菜单项。

**验收**：任何页面不再将家庭成员称为主用户；屏幕阅读器可朗读当前档案和切换动作。

## 实施分期

### 第一阶段：防错与明确性

实施第 1、2、3、4、10 项中的基础能力：身份条、首页空档案引导、上传确认、统一档案来源、AI 当前对象提示及术语整理。

### 第二阶段：档案资料与安全

实施第 6、7、8 项：成员级健康资料、可审计的数据删除/转移、成员级导出和分享。

### 第三阶段：家庭工作台

实施第 5、9 项：家庭概览、分层首页和跨档案摘要服务。

## 质量要求

- 每个档案级 router 查询必须通过 `getActiveProfileId(ctx.userId)` 或已校验的目标 `profileId` 过滤。
- 新增或修改档案归属的 mutation 必须验证 `profiles.user_id = ctx.userId`。
- 档案切换后使用完整页面重载，避免 React Query 跨档案复用缓存；长期方案是在所有档案级 query key 中包含 `profileId`。
- 为本人、无数据成员、有数据成员、非法 profile cookie、跨账号 profile ID 添加单元或集成测试。
- 每个阶段完成后执行 `pnpm --filter @openvitals/web typecheck` 和 `pnpm --filter @openvitals/web build`。
